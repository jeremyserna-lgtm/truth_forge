# Dimensional Framework

**The Essence** | Every concept in Truth Engine exists across multiple dimensions simultaneously. This framework formalizes all dimensions to ensure comprehensive analysis and prevent blind spots.

**Authority**: [07_STANDARDS.md](07_STANDARDS.md) | **Status**: CANONICAL

---

## Overview

The Dimensional Framework provides a **formal ontology** for analyzing any concept, system, policy, or decision across all relevant dimensions. It ensures that when we think about any single thing, we **automatically consider all perspectives** involved.

**Purpose**: Prevent blind spots by ensuring comprehensive dimensional analysis of every concept.

---

## Core Dimensions

Truth Engine operates across **twelve primary dimensions**. Every concept exists as a point in this multi-dimensional space.

### 1. SPATIAL_SCOPE (Where)

**Dimension**: Spatial or organizational scope

**Values**:
- `FEDERATION`: Across entire federation (all organisms)
- `GENESIS`: Genesis organism (Truth_Engine)
- `GENESIS_SEED`: Genesis-to-Seed relationship (parent-child)
- `ORGANISM`: Within a single organism
- `LOCAL`: Within a single system/service/module
- `INTERNAL`: Within a single component

**Example**: A policy can be `FEDERATION` scope (applies to all) or `ORGANISM` scope (applies to one).

### 2. TEMPORAL_SCOPE (When)

**Dimension**: Temporal or lifecycle scope

**Values**:
- `PAST`: Historical, archived, deprecated
- `PRESENT`: Current, active, in-use
- `FUTURE`: Planned, proposed, roadmap
- `EVERYTHING`: All time (past + present + future)

**Example**: A standard can be `PRESENT` (current version) or `FUTURE` (proposed change).

### 3. DOMAIN_SCOPE (What Domain)

**Dimension**: Subject area or domain

**Values**:
- `FRAMEWORK`: The Framework (00-07, patterns, principles)
- `STANDARDS`: Standards and conventions
- `SERVICES`: Central services
- `BIOLOGICAL`: Biological systems (vitals, membrane, consciousness, etc.)
- `INTELLIGENCE`: Intelligence systems (analysis, pattern mining, etc.)
- `FEDERATION`: Federation protocols and learning
- `GOVERNANCE`: Governance and compliance
- `INFRASTRUCTURE`: Infrastructure (storage, compute, network)
- `DATA`: Data management and storage
- `METABOLISM`: Metabolism and processing
- `IDENTITY`: Identity and lineage
- `MEMORY`: Memory and knowledge atoms
- `ARCHITECTURE`: System architecture
- `DEVELOPMENT`: Development tools and processes
- `DEPLOYMENT`: Deployment and operations

**Example**: A policy can be `GOVERNANCE` domain (compliance) or `FEDERATION` domain (learning).

### 4. TECHNOLOGY_SCOPE (What Technology)

**Dimension**: Technology stack or implementation

**Values**:
- `PYTHON`: Python code
- `TYPESCRIPT`: TypeScript/JavaScript code
- `MARKDOWN`: Markdown documentation
- `YAML`: YAML configuration
- `JSON`: JSON data
- `SQL`: SQL queries
- `SHELL`: Shell scripts
- `DOCKER`: Docker containers
- `CLOUD`: Cloud services (GCP, AWS, etc.)
- `DATABASE`: Databases (DuckDB, BigQuery, etc.)
- `API`: API interfaces
- `NETWORK`: Network protocols
- `CRYPTO`: Cryptographic systems
- `ALL`: All technologies (technology-agnostic)

**Example**: A standard can be `MARKDOWN` scope (document format) or `PYTHON` scope (code style).

### 5. AGENT_SCOPE (Who/What Agent)

**Dimension**: Agent or entity that interacts with the concept

**Values**:
- `GENESIS`: Genesis organism (Truth_Engine)
- `ORGANISM`: Daughter organisms (Zulip, etc.)
- `AI_AGENT`: AI agents (Claude, GPT, etc.)
- `DEVELOPER`: Human developers
- `SYSTEM`: System processes (automated)
- `IDE`: IDEs (Cursor, VS Code, etc.)
- `CI_CD`: CI/CD pipelines
- `USER`: End users
- `ALL`: All agents

**Example**: A policy can be `AI_AGENT` scope (agent behavior) or `DEVELOPER` scope (coding standards).

### 6. AUTHORITY_SCOPE (Who Has Authority)

**Dimension**: Who has authority over the concept

**Values**:
- `FEDERATION`: Federation authority (Genesis)
- `GENESIS`: Genesis authority
- `ORGANISM`: Organism authority (local)
- `DEVELOPER`: Developer authority
- `SYSTEM`: System authority (automated)
- `IMMUTABLE`: Immutable (cannot be changed)

**Example**: A policy can be `FEDERATION` authority (immutable) or `ORGANISM` authority (local control).

### 7. LIFECYCLE_SCOPE (Lifecycle Stage)

**Dimension**: Lifecycle or development stage

**Values**:
- `DESIGN`: Design phase
- `DEVELOPMENT`: Development phase
- `TESTING`: Testing phase
- `DEPLOYMENT`: Deployment phase
- `RUNTIME`: Runtime/operational phase
- `MAINTENANCE`: Maintenance phase
- `DEPRECATION`: Deprecation phase
- `ARCHIVE`: Archive phase
- `ALL`: All lifecycle stages

**Example**: A validation can be `DEVELOPMENT` scope (pre-commit) or `RUNTIME` scope (runtime enforcement).

### 8. INTERFACE_SCOPE (How Accessed)

**Dimension**: Interface or medium through which concept is accessed

**Values**:
- `CLI`: Command-line interface
- `API`: API interface
- `FILE_SYSTEM`: File system operations
- `DATABASE`: Database operations
- `NETWORK`: Network operations
- `UI`: User interface
- `WEBHOOK`: Webhook interface
- `STREAM`: Streaming interface
- `ALL`: All interfaces

**Example**: A service can be `API` scope (REST API) or `CLI` scope (command-line tool).

### 9. GRANULARITY_SCOPE (Level of Detail)

**Dimension**: Level of granularity or abstraction

**Values**:
- `ENTERPRISE`: Enterprise-wide
- `SYSTEM`: System-wide
- `SERVICE`: Service-level
- `MODULE`: Module-level
- `COMPONENT`: Component-level
- `FUNCTION`: Function-level
- `LINE`: Line-level (code)
- `ALL`: All granularities

**Example**: A standard can be `SYSTEM` granularity (system-wide) or `COMPONENT` granularity (component-specific).

### 10. PERSISTENCE_SCOPE (How Stored)

**Dimension**: Persistence or storage mechanism

**Values**:
- `MEMORY`: In-memory only
- `FILE`: File-based storage
- `DATABASE`: Database storage
- `CLOUD`: Cloud storage
- `VERSIONED`: Version control (Git)
- `CACHE`: Cached storage
- `TRANSIENT`: Transient (no persistence)
- `ALL`: All persistence mechanisms

**Example**: Data can be `FILE` persistence (JSONL files) or `DATABASE` persistence (DuckDB).

### 11. CHANGE_SCOPE (Mutability)

**Dimension**: How the concept can change

**Values**:
- `IMMUTABLE`: Cannot be changed (federation policies)
- `MUTABLE`: Can be changed
- `VERSIONED`: Changes tracked via versioning
- `DYNAMIC`: Changes at runtime
- `STATIC`: Static (unchanging)
- `EVOLVING`: Evolves over time

**Example**: A policy can be `IMMUTABLE` (federation policy) or `MUTABLE` (organism policy).

### 12. PURPOSE_SCOPE (Why/For What)

**Dimension**: Purpose or use case

**Values**:
- `GOVERNANCE`: Governance and compliance
- `SECURITY`: Security and protection
- `QUALITY`: Quality assurance
- `OPERATIONS`: Operations and maintenance
- `DEVELOPMENT`: Development and coding
- `LEARNING`: Learning and knowledge
- `COMMUNICATION`: Communication and federation
- `ANALYSIS`: Analysis and intelligence
- `STORAGE`: Storage and data management
- `PROCESSING`: Processing and transformation
- `ALL`: All purposes

**Example**: A system can be `GOVERNANCE` purpose (compliance) or `LEARNING` purpose (knowledge extraction).

## Dimensional Analysis

### Analyzing a Concept

When analyzing any concept, ask:

1. **SPATIAL_SCOPE**: Where does this apply? (Federation, Genesis, Organism, Local)
2. **TEMPORAL_SCOPE**: When does this apply? (Past, Present, Future)
3. **DOMAIN_SCOPE**: What domain? (Framework, Standards, Services, etc.)
4. **TECHNOLOGY_SCOPE**: What technology? (Python, Markdown, API, etc.)
5. **AGENT_SCOPE**: Who uses this? (AI Agents, Developers, Systems, etc.)
6. **AUTHORITY_SCOPE**: Who controls this? (Federation, Genesis, Organism)
7. **LIFECYCLE_SCOPE**: What stage? (Design, Development, Runtime, etc.)
8. **INTERFACE_SCOPE**: How accessed? (CLI, API, File System, etc.)
9. **GRANULARITY_SCOPE**: What level? (Enterprise, System, Service, etc.)
10. **PERSISTENCE_SCOPE**: How stored? (File, Database, Memory, etc.)
11. **CHANGE_SCOPE**: Can it change? (Immutable, Mutable, Versioned)
12. **PURPOSE_SCOPE**: Why exists? (Governance, Security, Learning, etc.)

### Dimensional Checklist

For every concept, ensure you've considered:

- [ ] All relevant spatial scopes
- [ ] All relevant temporal scopes
- [ ] All relevant domains
- [ ] All relevant technologies
- [ ] All relevant agents
- [ ] Authority implications
- [ ] All lifecycle stages
- [ ] All interfaces
- [ ] Granularity implications
- [ ] Persistence implications
- [ ] Change implications
- [ ] Purpose alignment

## Dimensional Relationships

### Inheritance Rules

**Spatial Inheritance**:
- FEDERATION → GENESIS → ORGANISM → LOCAL
- Higher scopes apply to all lower scopes
- Lower scopes can refine but not override critical policies

**Temporal Inheritance**:
- FUTURE → PRESENT → PAST
- Present inherits from past
- Future builds on present

**Domain Relationships**:
- FRAMEWORK → STANDARDS → SERVICES
- Framework principles inform standards
- Standards guide service implementation

### Dimensional Conflicts

When dimensions conflict:

1. **Authority Wins**: Higher authority overrides lower
2. **Immutability Wins**: Immutable overrides mutable
3. **Scope Wins**: More specific scope wins
4. **Purpose Wins**: Primary purpose takes precedence
